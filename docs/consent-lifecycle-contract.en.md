# Cloud consent, retry, and audio lifecycle contract (Issues #2 and #3)

**Status: candidate specification; not implemented or accepted.** Baselines: program main `48a0bcad14373728e24955264bc5ceddd4981622`, published #2 document `e5e6abf085ca544f27613a1c4a203b8189c66af6`, and the text and 2026-11-01 independent review of #3. This contract resolves the identified decisions without replacing the remaining original acceptance criteria. Two previously described unpushed local specifications are unavailable here: they were not read, overwritten, or claimed to be synchronized. The [Traditional Chinese version](consent-lifecycle-contract.zh-TW.md) states the same contract.

## C1. Identity and default consent

Before the first external transmission, explain that audio travels through the local bridge to an unofficial ChatGPT transcription endpoint, the purpose and transmission method, and that cancellation cannot retract sent data. Offer “Agree and send”, “Cancel”, and an unchecked-by-default “Remember my choice”. Refusal, closing, or cancellation sends nothing. If saving fails, do not claim the choice was remembered; the current request may proceed only after explicit consent and the next request must ask again. Do not store audio, transcripts, keys, or tokens as consent records.

Reusable consent must bind a versioned tuple of verified actual recipient identity, purpose, transmission method, and consent-text version, plus consent time. A trusted mechanism must verify the **actual forwarding path for each send**. A local URL, successful health check, self-declared string, or running process is insufficient. The current bridge provides no such mechanism: treat identity as unknown, make remembering ineffective and explain why, and ask before every send. Never present a hard-coded expected upstream as verified. A future trusted mechanism requires separately reviewed evidence of its source, verification, and invalidation; this specification does not presume it exists.

Missing, damaged, unreadable, unverifiable, or changed tuple fields or text version invalidate consent and require a new prompt. Settings must show cloud-recognition status, recipient/purpose/transport explanation, valid or unknown reason, and “Revoke consent”. Revocation immediately removes reusable authorization for the current process; the next request needs fresh consent. It cannot retract sent data or claim to stop server-side processing. Save/revoke failures must be visible and never reported as successful; even if persistence fails, the process must fail closed and refuse to reuse the old record. On restart, an old record cannot be represented as durably revoked after a failed write; show a repair path and ask on every request whenever the state cannot be established.

## C2. Retry is a separate decision

Never resend automatically. After the user explicitly chooses retry, if a previous request may have been sent but its result is unknown (for example disconnect, timeout, cancellation after send, or unknown server error), separately warn of possible duplicate processing and possible charges and require explicit “Retry anyway”. Cancel, close, or refusal sends nothing. This is not recipient consent; first complete the necessary risk confirmation, then obtain or validate C1 consent, and send only after both guards pass. For a failure known not to have sent a request, the unknown-result warning is unnecessary, but C1 still applies. Remembering recipient consent never skips risk confirmation.

## C3. Cancellation, ownership, and concurrency

Allow at most one recording, import, or transcription job per app process. Cancellation immediately updates the UI, requests cancellation, and invalidates that job generation; late success or failure must not change UI, history, clipboard, or a later job. Until the old request and all streams actually end and release, prohibit new recording, import, sending, and retry. Show “Finishing the previous job”; do not claim cleanup. If it never releases, retain the protected file and provide a close-app instruction. Normal shutdown waits at most five seconds; after timeout the app may exit but must report cleanup pending, must not kill another process, and must not guarantee server-side cancellation.

App-owned recordings and import snapshots use a dedicated work directory; never delete or overwrite the user's source import. Each launch uses a non-reusable random directory ID restricted to the user's ACL and rejects links, junctions, or reparse points escaping the root. Every active owner acquires and holds a cross-process, cross-Windows-session exclusive OS lock before using its directory. A cleaner first acquires a nonblocking exclusive lock on the same stable lock object; if unavailable or unverifiable, it skips the directory without reading, writing, or deleting it. Lock names cannot be reused; the cleaner holds the lock throughout cleanup, and the lock object cannot be deleted and recreated during a race. If the platform cannot supply these lock and safe-path guarantees, disable automatic cleanup rather than guessing whether a directory is idle. This is an implementation contract, not a claim that Windows locking is already implemented.

Clean only residual files provably owned by the app, with no active owner, and older than 24 hours; skip when time is untrustworthy, the clock moves backwards, or ownership/path is uncertain. After success, abandonment, or cancellation, clean only after all streams are released and the lock is held. A deletion failure must not be shown as success; retain it for a later eligible launch. Files under 24 hours may remain until a still later launch. Diagnostics contain only safe error category, time, and anonymous job ID, not file paths, content, or secrets.

## C4. Import consistency

Accept only verifiable local regular files on storage with the required locking semantics; stop for network files, reparse points, or unverifiable semantics. This does not claim protection from malware with system-level write access. Before each send, use a Windows file handle that permits read sharing but denies other writes/deletes to hold the source fixed and create an app-owned snapshot. Validate snapshot format, duration, size, and SHA-256 before showing consent. Hold the source handle through consent and the start of sending, and verify source file identity, size, and hash still match the snapshot. If the guard cannot be acquired or maintained, the source changes, a read fails, or comparison fails, stop and send nothing. Re-select, recreate and validate the snapshot, and obtain fresh consent for that attempt. After writing the snapshot, open it read-only with sharing that denies other writes and deletes. Validate format, size, duration, and hash using this **same handle** and hold it throughout consent; immediately before sending, recheck file identity, size, and hash. Any mismatch, lost protection, or unverifiable state means zero transmission. Rewind and stream from that same handle until the request finishes and releases; never reopen the snapshot by path. Send only this validated snapshot, never reopen the source path for transmission. The snapshot is also protected by C3 locking and cleanup; never delete the user's original. Retry must revalidate audio availability; if the source or snapshot changed or cannot be verified, treat it as new data requiring fresh confirmation.

## C5. Reproducible acceptance (all pending)

- Table-test first use, not remembered, explicitly remembered, restart, revoke, save/revoke failure, corrupt settings, each tuple/text-version change, and unknown identity; record consent prompts and request counts. The current bridge asks every time; only a verifiable fake provider tests the reusable branch.
- Test known-unsent and unknown-result failures. The latter requires the independent risk confirmation even with remembered consent; refusing either required guard sends zero requests. Repeated clicks do not duplicate sends. A mock is not evidence of real service success.
- Across processes and two Windows sessions test held locks, lock races, abnormal exit, clock rollback, under/over 24 hours, reparse points, deletion and lock failures. Active data is never deleted; failures are visible without sensitive logs. If lock semantics cannot be established, mark BLOCKED, not PASS.
- Control a never-releasing request, late success/failure, cancellation, and shutdown timeout; verify that new work is blocked, stale results ignored, and files protected. Simulate source rewrite, replacement, deletion, or inability to lock before consent; each causes zero sends and leaves original bytes unchanged. Attempt snapshot rewrite, deletion, or replacement through another handle during consent and before send; a verification mismatch or loss of protection must send zero requests. On the normal path verify bytes sent from the same protected handle equal the validated snapshot.
- On Windows at 100% and 150% scaling, in dark/light themes, test keyboard focus, screen-reader names, minimal/normal window, navigate from the main window by mouse or keyboard through “Settings” → “Cloud recognition and consent”, then inspect status, revoke and its outcome. Each control must have a recognizable accessible name, support Tab/Shift+Tab and Enter/Space, and show visible focus. A revoke failure remains visible and is announced as an accessible screen-reader status/alert; record resolution and results. Measure against WCAG 2.2 AA contrast (normal text 4.5:1, large text 3:1, essential controls 3:1) and record exceptions. Both English and Traditional Chinese READMEs must explain remember/revoke/invalidation/unknown and the separate retry warning; never rewrite user transcripts.
- Actual Windows ASR, login, recording/import, and real audio transmission require separate consent for that test. Mock, health, or document acceptance is not successful real transcription. The four unresolved #2 items and original #3 acceptance criteria remain open.
